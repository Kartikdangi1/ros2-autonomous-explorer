# Autonomous Exploration with a Reinforcement-Learning Local Planner

Exploring an unmapped indoor space autonomously requires two separate decisions at two separate timescales: where to go next, decided once every few seconds from the current map, and how to get there safely, decided many times a second from the current sensor readings. This repository implements both halves for a four-wheel Mecanum-drive robot in Gazebo, a classical next-best-view planner for the first decision and a choice of a conventional or a reinforcement-learning-trained controller for the second, and keeps the two decoupled enough that either local planner can sit underneath the same exploration logic without the exploration layer knowing which one it is talking to.

The reinforcement-learning planner is trained inside MuJoCo rather than Gazebo, reported by the repository's own documentation to run ten to forty times faster for this purpose, and is exported to ONNX so the trained policy runs on the same real-time inference path in Gazebo deployment as it did in simulation. The gap between a policy that works in training and one that works when deployed is closed structurally, not by hoping the two environments happen to agree, since the same observation and action interface is implemented once for each environment rather than adapted after the fact.

## Background and Motivation

A classical local planner such as DWB reacts to obstacles using a hand-tuned cost function, and tuning that function well for a Mecanum-drive platform, which can translate and rotate independently in ways a differential-drive cost function does not anticipate, is its own separate exercise in each new environment. A learned controller can in principle absorb that tuning into training rather than into manual parameter search, provided training itself is fast enough to iterate on and provided the trained policy transfers to the platform it will actually run on. Both conditions motivate the specific architecture chosen here: MuJoCo for throughput during training, and a matched observation and action contract so a policy trained in one simulator deploys unchanged in the other.

## Implementation

### Classical exploration

Frontier-based next-best-view exploration is implemented from four cooperating components rather than assembled from an existing Nav2 exploration plugin. A Bayesian log-odds occupancy grid accumulates evidence from the robot's sensors over time; a frontier extractor identifies the boundary between explored and unexplored space by detecting jump edges across angular sectors of the grid rather than by a more expensive full-image edge detector; a candidate generator proposes viewpoints along that boundary; and a scorer ranks each candidate by ray-casting from it to estimate how much unexplored area it would actually reveal, since a candidate adjacent to a large unexplored region is not useful if a wall between the two blocks the view. A mission-control node runs this loop and hands the winning candidate to Nav2's behaviour-tree navigator as a goal pose, so the exploration logic decides where to go while Nav2's own planner and controller decide how to get there without either being duplicated.

The launch sequence brings up Gazebo, an extended Kalman filter fusing odometry sources, SLAM Toolbox, Nav2 and the exploration node itself, staggered with explicit timer delays rather than launched simultaneously, since several of these nodes depend on services or transforms that the node before it in the sequence has not yet published at the moment a simultaneous launch would start them.

### Reinforcement-learning local planner

The observation the controller receives is deliberately narrow and platform-relative rather than a raw map: an eighty-four by eighty-four local costmap centred on the robot, three hundred and sixty normalised LiDAR ranges, a two-value goal vector giving direction and distance in the robot's own frame, and a three-value velocity readout. The action is a three-value normalised velocity command, forward, lateral and yaw rate, matching the Mecanum platform's actual degrees of freedom rather than the two degrees of freedom a differential-drive convention would assume. Both the observation builder and the reward function are shared code paths between the MuJoCo training environment and the Gazebo deployment environment, so a change to either is a single edit rather than two that could drift out of agreement.

Reward shaping combines eight components, progress toward the goal, heading alignment, an additional shaping term near the goal, a terminal bonus on success, a collision penalty, a proximity penalty for approaching an obstacle without yet colliding, a smoothness term penalising abrupt action changes, and a small constant step cost discouraging unnecessarily long paths. A four-stage curriculum increases goal distance from 0.3 to 6 metres, promoting the agent to the next stage automatically once its success rate at the current stage clears a threshold, rather than training against the hardest configuration from the first step and hoping early learning survives it.

Inside MuJoCo, the robot body carries a free joint rather than individually actuated wheel joints, and velocity is written directly into the physics engine's velocity state each simulation step; this is a deliberate simplification that trades wheel-level realism for the training throughput the repository's own documentation cites as the reason for using MuJoCo in the first place, and it is stated here as a simplification rather than left for a reader to discover by inspecting the model. LiDAR is simulated with three hundred and sixty individual ray casts per step rather than a single approximated sweep, since the costmap the policy conditions on depends on per-ray occlusion, and an approximated sweep would feed the policy a subtly different signal from the one it receives once deployed against a real LiDAR driver.

A custom feature extractor for the underlying proximal policy optimisation algorithm splits the observation into a convolutional branch for the costmap and a multilayer-perceptron branch for the scan, goal vector and velocity, rather than flattening every input into one vector, on the reasoning that a costmap benefits from spatial structure a flattened vector discards. Trained policies are exported to ONNX and run inference on a real-time ROS 2 node at ten hertz, extracting a carrot point ahead of the robot along the global path Nav2 has already planned and feeding that carrot point into the observation the policy was trained against; a hard-coded safety layer can override the policy's output with an emergency stop independently of whatever the policy itself outputs, so a policy failure degrades to a stop rather than to unconstrained motion.

### Configuration validation

Training configuration is defined through a set of typed models validated at load time, so a mistyped reward weight or an out-of-range curriculum parameter raises an error before training starts rather than silently falling back to a default partway through a multi-hour run. This is a small addition relative to the reinforcement-learning code itself, but it addresses a failure mode specific to long-running training jobs: a configuration mistake that would otherwise only be discovered by noticing that a training curve looks wrong hours after the mistake was made.

## Validation

Reward computation, curriculum promotion logic and observation construction each have dedicated test coverage, checked with a linter as part of the same test pass. Hyperparameter search is run through an automated sweep rather than manual trial and error, and training progress is monitored through a standard experiment-tracking dashboard so a promising or a stalled run is visible without waiting for training to finish.

## Limitations

Velocity being written directly into the physics state rather than driven through simulated wheel actuation means the MuJoCo training environment does not model wheel slip or motor dynamics, and any behaviour depending on either would need to be learned or validated in Gazebo instead, where those dynamics are present. The saved normalisation statistics accompanying a checkpoint must be loaded alongside it for inference to be correct, since the policy was trained against normalised observations; a checkpoint used without its matching normalisation file would receive observations on a different scale from the ones it was trained on, producing degraded rather than absent behaviour, which is a harder failure to notice than an outright error.

## Further Work

Extending the reward function and curriculum to a second robot platform with different kinematics would be the natural test of how much of the current design generalises beyond the Mecanum-specific action space it was built around. Closing the gap between MuJoCo's simplified actuation and Gazebo's fuller physics remains open, and the safety e-stop layer already in place is the mitigation for that gap at deployment time rather than a substitute for eventually modelling the missing dynamics in training.
